# 语音朗读（TTS）方案

> 状态：**方案已定，待实施** ｜ 建立日期：2026-09-10
> 定位：适老化能力的 P4，与「大字·清晰版」**并列但独立**的能力，不捆绑上线
> 依赖：腾讯云语音合成 TTS —— **复用现有 ASR 的同一套 SecretId / SecretKey 与 TC3 签名代码**，不需要新账号、新密钥、新供应商

## 一、结论速览

| 项 | 结论 |
|---|---|
| 读什么 | **只读「内容型正文」三处**：AI 回答、在线营养师回复、营养师补充留言 |
| 不读什么 | 界面型文字一律不读：用户自己的提问、首页聚合区、等待面板、系统/状态提示、社区 UGC |

## 二、朗读范围（本次核心决策）

判断标准一句话：**用户在屏幕上看的是什么「内容」，就读什么；屏幕上的「界面元素」一律不读。**

### 2.1 三档分类

| 档 | 对象 | 理由 |
|---|---|---|
| **建议读** | ① AI 回答气泡 ② 在线营养师回复 ③ 营养师补充留言 | 这是用户专门来获取的信息本体；对不识字/视力差的老人价值最高 |
| **可选读** | ④ 资讯正文 ⑤ 案例详情 ⑥ 产品详情 | 都是有价值的正文，但长、且格式复杂，第二期再做 |
| **不读** | 用户自己的提问、首页快捷/热门区、等待面板步骤、系统与转人工提示、社区 UGC | 见 2.3 |

### 2.2 建议读的三处，精确到取值

| # | 对象 | 取哪个字段 | 文本格式 | 代码位置 |
|---|---|---|---|---|
| ① | AI 回答 | `state.messages[i].content`（`role === 'bot'`） | **原始 Markdown 纯文本**（不是 DOM！） | 写入：`chat.js:87 addMessage` / `chat-misc.js:409 addBotMessage` / `chat-stream.js:55`（流式增量累加）<br>渲染：`chat.js:53 renderBotContent` |
| ② | 在线营养师回复 | `msg.content`（`role === 'handoff-agent'`） | 纯文本（渲染时才 `escapeHtml`） | `chat.js:106` |
| ③ | 营养师补充留言 | `nutritionist-notes.js` 对应字段 | 纯文本 | `static/js/nutritionist-notes.js` |

> ⚠️ ① 的关键：`msg.content` 存的是**带 Markdown 标记的原文**（`**加粗**`、表格管线符、三个反引号包裹的代码块、`- 列表`）。朗读前必须剥离标记（见第三节），否则 TTS 会念出「星号星号」「竖线竖线」。

### 2.3 为什么这五类不读

| 不读对象 | 原因 |
|---|---|
| 用户自己的提问 | 字是用户刚打的，他知道自己问了什么；读一遍纯属噪音 |
| 首页聚合区（快捷功能 / 示例问题 / 热门问题） | 一堆半截短句聚在一起，读出来是噪音，不是内容 |
| 等待面板步骤文案 | `renderWbContent` 每 3.5 秒自动换一句、还有光标动画；读一半内容就变了 |
| 系统消息、转人工状态提示 | 非内容，是状态指示 |
| 社区 UGC（问题与回复） | 他人撰写、质量不可控、未经本人同意；且是审核后内容，朗读价值低 |

## 三、文本预处理规则（必做，否则体验崩坏）

### 3.1 AI 回答：Markdown 剥离

`renderBotContent()`（`chat.js:53`）已实现一套轻量 Markdown 规则，朗读需要**反向**处理：

| Markdown 元素 | 原文形态 | 朗读处理 |
|---|---|---|
| 加粗 | `**文字**` | 去掉 `**`，直接读「文字」 |
| 无序列表 | `- 文字` / `* 文字` | 去掉行首符号，读「文字」（多条可加「第一、第二」或直接顺序读） |
| 代码块 | 三个反引号包裹 | **整块跳过**，不提示 |
| 表格 | `\| a \| b \|` + 分隔行 | **跳过并提示**：读一句「此处有一张表格，请查看屏幕」 |
| 分隔符 / 多余空行 | `---`、连续换行 | 压缩为单个停顿 |

> 决策已定：**表格 = 跳过并提示；代码块 = 静默跳过。**
> 理由：逐行念表格会变成「竖线 产品 竖线 功效」，体验极差；完全静默又会让用户以为漏了内容。

### 3.2 资讯 / 产品正文：HTML 提取（第二期）

资讯正文（`news-discover.js:462 renderNewsDetail`）和产品正文（`utils-products.js:109 showProductDetail`）的 `content` 字段是 **HTML（Quill 富文本）**。

**绝对禁止直接读 `innerHTML`** —— 会念出标签名、属性、图片 URL、alt 文本。正确做法：

```
DOM 解析 → textContent 提取纯文本 → 剔除 img / svg / 按钮节点 → 压缩连续空白
```

实现上可直接复用现有 `renderNewsDetail` 里那个临时 `div` 的模式，但取 `textContent` 而非 `innerHTML`。

### 3.3 长度与分段

基础语音合成**中文单次上限 150 个汉字**（全角标点算 1 个汉字；英文 500 字母；汉字/字母/数字/标点/空格/回车均按 1 字符计费）。

分段策略：
1. 按句末标点（`。！？；\n`）切分，**累积到接近 150 字**为一段，不硬切到一半句子；
2. 单句本身超 150 字（罕见的超长句）→ 按逗号二次切分；
3. 段数上限兜底：超过 20 段（约 3000 字）时只合成前 20 段，末尾追加一句「内容较长，剩余部分请查看屏幕」。

## 四、后端设计

### 4.1 复用现有签名（核心：改动极小）

`services/speech_service.py:79 _tencent_api_request(action, payload, secret_id, secret_key)` 目前把三个常量写死在函数体里。只需**参数化这三个值**即可同时服务 ASR 与 TTS：

| 项 | ASR（现有） | TTS（新增） |
|---|---|---|
| host | `asr.tencentcloudapi.com` | `tts.tencentcloudapi.com` |
| service | `asr` | `tts` |
| version | `2019-06-14` | `2019-08-23` |
| Action | `SentenceRecognition` | `TextToVoice` |

凭据复用：
- `tencent_secret_id` —— 明文 setting
- `tencent_secret_key` —— 加密 setting，走 `services.secret_service.get_secret_setting`

> 注意：`speech_enabled`、`speech_mode` 是语音**输入**的开关和数据，**朗读必须用独立开关 `tts_enabled`**，两者互不牵连（后台可能只想开朗读不想开录音）。

### 4.2 接口形态选型（重要成本决策）

腾讯云 TTS 提供四种形态：

| 接口 | 协议 | 最大字数 | 免费额度 | 单价（后付费） | 本方案 |
|---|---|---|---|---|---|
| 基础语音合成 `TextToVoice` | REST 同步 | 150 汉字 | **享受 800 万字符** | 精品 0.3 元/万字符 | ✅ **采用** |
| 长文本合成 `CreateTtsTask` | REST 异步 | 10 万字符 | **不享受免费额度** | 精品 2.0–2.8 元/万字符 | ❌ 不用 |
| 流式文本合成 | WebSocket | 10000 字/会话 | — | — | ❌ 二期再说 |
| 实时语音合成 | WebSocket | — | — | — | ❌ 不适用 |

**结论：全部走基础语音合成，长文本也分段调它。**
长文本接口虽然一次能吞 10 万字很省事，但两点致命：
1. 它**不参与 800 万字符免费额度**；
2. 单价 2.0–2.8 元/万字符，是精品的 **7–9 倍**。

一段 5000 字资讯走长文本接口要花 1.2–1.4 元；走基础接口分段调，只消耗免费额度（0 元）。**用 33 次请求换取成本归零，完全值得。**

### 4.3 缓存（必须做，否则热门回答重复烧钱）

- 缓存键：`md5(归一化文本 + voice_type + model_type + speed)`
- 存法：合成结果 mp3 落盘到 `static/uploads/tts/`（或独立 `TTS_CACHE_DIR`），DB 或文件名直接做索引
- 返回时带 `Cache-Control: public, max-age=604800` + `ETag`
- 效果：同一条 AI 回答被 100 个人听，只计费 1 次
- 清理：后台加一个「清空朗读缓存」按钮，或按最后访问时间 LRU 过期（建议 30 天）

### 4.4 限流与开关

- **限流**：沿用 `services/security_service.rate_limit`，装饰器风格与 `routes/speech.py` 一致。建议按 user_id + IP 双维度，窗口 600 秒。
- **开关**：新增 setting `tts_enabled`。
  - 关闭 / 未配置 SecretId 或 SecretKey → 接口直接 403，**且前端不渲染「听」按钮**（不留点了没反应的死按钮）。
  - 前台通过 `/api/speech/config` 一并下发 `tts_enabled`（该接口已存在，扩展字段即可，不新增接口）。

### 4.5 新增接口

```
POST /api/tts
  body: { text: string, voice_type?: int }
  resp: audio/mpeg（二进制 mp3）
        或 JSON { error, retryable } （失败时）
```

- 装饰器：`@identity_required` + `@rate_limit('tts', ...)`（与现有 speech 路由一致）
- 服务端负责：文本预处理（第 3 节规则）→ 分段 → 逐段调 `TextToVoice` → 拼接
  - **v1 简化**：只合成**第一段**返回 + 剩余段落在响应头告知；前端按需逐段请求
  - **v2（推荐）**：服务端一次性把全部段落合成好并拼接成单个 mp3 返回（服务端有缓存，重复成本低）
- 失败降级：合成失败返回 JSON 错误，前端 toast「朗读暂不可用」，不影响其他功能

## 五、前端设计

### 5.1 按钮落点（已修订：不放操作行）

> ❗**修订说明（2026-09-10）**：初稿建议把「听」并入 `msg-actions` 操作行。实测该行尺寸后**否决此方案**，
> 理由见下表 —— 它对适老化目标用户等于不可用。

**现状实测**（`static/css/chat-ui.css:112-144`）：

| 属性 | 实际值 | 适老化标准 | 判断 |
|---|---|---|---|
| `.msg-action-btn` 高度 | **28px** | WCAG 2.5.5 ≥44px / 工信部建议 60px | ❌ 仅达标六成 |
| 字号 | 11px | 正文 ≥18px | ❌ |
| 内边距 | `4px 6px` | — | 偏小 |
| 行内间距 | `gap: 2px` | 相邻热区需防误触 | ❌ 极易点错 |
| 换行 | `flex-wrap: wrap` | — | 再加按钮会折行，更挤 |

**结论：朗读是适老化功能，入口尺寸必须比现有操作行大一个量级。操作行本身就偏小，不能再往里塞。**

**采用方案：气泡下方独立「朗读条」**

```
┌─────────────────────────────┐
│  气泡正文 ……                │
└─────────────────────────────┘
┌─────────────────────────────┐   ← 新增：高 48px，宽撑满
│  🔊  朗读这条回答            │      border: 1px #0F6E56
└─────────────────────────────┘
复制   查看产品   重新回答         ← 原操作行不动
```

| 项 | 规格 | 理由 |
|---|---|---|
| 高度 | **48px**（大档 52px） | 超过 44px 底线，热区约为原小按钮的 3 倍 |
| 宽度 | 撑满气泡宽（254px） | 整条可点，不需要瞄准 |
| 文案 | 写全「朗读这条回答」 | 不用猜图标含义；播放中切「停止朗读」 |
| 位置 | 气泡与操作行**之间** | 与回答内容紧邻，语义最近；不占用操作行 |
| 边框 | `1px solid #0F6E56` + 浅底 | 弱存在感但不隐形，视觉上是「次级主按钮」 |

**适用范围与降级规则：**

1. **只读回答，不读用户消息** → 仅 `role === 'bot'` 和 `role === 'handoff-agent'` 两种消息渲染朗读条。
2. **显示范围（已定）**：**最新一条回答挂 48px 大朗读条；历史回答降级为操作行里的一个 `speaker` 小图标**（仍可点击朗读）。
   理由：长对话里每条都挂 48px 朗读条会严重臃肿，而朗读的主场景是「刚生成完就听」；历史回答保留小图标兜底，不丢能力。
   > ⚠️ 已知折衷：历史回答的小图标受制于 `.msg-action-btn` 的 28px 尺寸，对老人偏小（见本节约 5.1 开头的实测）。
   > 这是有意接受的代价 —— 若后续把整行操作按钮统一放大到 44px（见下方备选），此处会自动受益。
3. **不做「自动朗读」总开关（已定）**：只保留手动点击。理由：微信里默认外放会尴尬，且自动播报难以中断。
   代价是「完全不识字」的极端用户仍需先找到按钮 —— 通过大尺寸朗读条 + 显式文案尽量降低这层门槛。
4. **`tts_enabled=0` 或未配置密钥时，朗读入口整个不渲染**（大条和小图标都不渲染），不留死按钮。
5. **图标**：沿用 `static/icons/` 的 SVG 体系，新增 `speaker` / `speaker-stop` 两枚；若走 JS 动态渲染路径，**必须同步补 `icon-fallback.css` 的 `i.ph-*` 映射**，否则会渲染成纯色实心块（项目已知坑）。

**未采用的两个备选：**

| 备选 | 否决理由 |
|---|---|
| 把整行 `.msg-action-btn` 统一放大到 44px | 改动面覆盖全站所有操作按钮，回归风险大；且 5 个按钮 × 44px 在 480px 容器里必然折行，反而更乱。可作为**独立**的适老化改进项另排期 |
| 长按气泡朗读 | 无可见入口，老人发现不了；且微信里长按会触发文字选中与系统菜单，**不可作主路径** |

### 5.2 状态机

```
idle ──点击「听」──> loading（合成中，按钮转圈）
  ↑                    │
  │                    ▼
  └── 播完/出错 ◀── playing（播放中，按钮变「停止」）
                       │ 点击
                       ▼
                    stopped
```

- 全局**同时只允许一条回答在播**：点第二条时先停掉第一条（避免串音）
- 播放中按钮文案切「停止」，图标切 `speaker-stop`
- 切换视图、清空对话、进入人工会话时，自动停止播放

### 5.3 分段播放与预取

- 前端维护一个播放队列：`[segment1, segment2, ...]`
- 第一段**必须在用户点击手势内开始播放**（微信/iOS 的自动播放限制，见风险表）
- 后续段落串行预取（并发 2–3 段），当前段播完立即接上，避免段落间明显卡顿
- 合成请求走 `AbortController`，用户点「停止」时中止未完成的请求

## 六、成本核算（2026-09 官方数据，已核实）

| 项 | 数值 |
|---|---|
| 免费额度（基础/精品音色） | **800 万字符**，仅通用语音合成接口，领取后 3 个月有效，一个账号一次 |
| 精品音色后付费单价 | 0.3 元/万字符（不区分梯度） |
| 大模型音色后付费单价 | 0.55–1.2 元/万字符（按日用量梯度） |
| 计费口径 | 汉字、字母、数字、标点、空格、回车**均按 1 字符计** |

**估算**：一条 AI 回答按 500 字计 → 精品音色 0.015 元/次；800 万字符 ≈ **1.6 万次**朗读。中小流量下前期基本零成本。

> 实际成本还会因缓存（4.3）进一步降低 —— 同一问答只计费一次。

### 6.1 场景测算（300 字/条 × 100 条/天）

> 假设：每条回复 300 字，每天 100 条回复被朗读，自然月按 30 天计。
> **不含标点**时 300 字 = 300 字符；实际含标点约 330 字符，成本上浮约 10%，下表按 300 字符保守计。

**用量**：日 3 万字符 → 月 **90 万字符** → 年 1,080 万字符。

| 音色档 | `ModelType` | 免费额度 | 免费额度能撑多久 | 用尽后月成本 | 首年总成本 |
|---|---|---|---|---|---|
| **基础 / 精品** | 1 / 2 | 800 万字符 | 额度够 8.9 个月，但**有效期仅 3 个月** → 实得 270 万字符 | **27 元/月** | **约 243 元** |
| 大模型 | 3 | 10 万字符 | 约 **3.3 天** | 108 元/月 | 约 1,280 元 |
| 超自然大模型 | — | 2 万字符 | **不到 1 天** | 585 元/月 | 约 7,000 元 |

**结论：按月 90 万字符算，走精品音色，首年总投入约 243 元。**

**三个必须知道的细节：**

1. **免费额度是「一次性 + 3 个月有效期」，不是每月刷新。**
   800 万字符按本量能用 8.9 个月，但资源包自领取起 **3 个月内有效，过期作废，一个账号只能领一次**。
   即：3 个月实际只消耗 270 万字符，**剩余约 530 万字符直接作废**。所以「首年 243 元」= 前 3 个月 0 元 + 后 9 个月 × 27 元。

2. **不要提前领免费资源包。** 有效期从领取那一刻开始跑。建议**等朗读功能真正上线那天再去控制台领取**，否则功能还没做完额度就烧掉一半。而且不领 = 额度为 0，直接走付费，所以「什么时候领」是个真实的成本决策点。

3. **预付费资源包在本量级不划算。** 精品音色最小规格是 1 亿字符 / 2,100 元（0.21 元/万字符）。本场景年用量仅 1,080 万字符，后付费 324 元/年远低于买包，**直接走按量付费即可**。

**缓存能再省多少**：AI 客服场景问题重复率高（产品功效、用法类问答高度雷同）。若缓存命中 35%，付费期月成本从 27 元降到约 **17.6 元**。缓存不是优化项，是必做项（见 4.3）。

**与「用长文本接口」的对比**：同样的 90 万字符/月，长文本接口精品音色按 2.8 元/万字符 = **252 元/月**，且**不享受那 800 万免费额度**。即第一个月就要掏钱，一年近 3,000 元 —— 是分段调用基础接口的 **12 倍以上**。这从成本侧再次印证 4.2 的选型结论。

## 七、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **微信/iOS 自动播放限制** | 后续段落被浏览器拦截，只播了第一段 | 第一段在点击手势回调内启动；被拦时退化为「点一下播下一段」，不做静默失败 |
| 无缓存导致重复计费 | 热门回答被反复听，成本线性膨胀 | 强制走 md5 缓存（4.3），这是**必做项**不是优化项 |
| 长文本一次合成超限 | 接口报错 | 严格按 150 汉字分段（3.3），前端控制段数上限 |
| 直接读 `innerHTML` | 念出标签、图片 URL，体验崩坏 | 统一走 `textContent` 提取（3.2） |
| 流式回答逐字朗读 | 断续刺耳 + 成本翻几十倍 | **只在 `done` 事件后读一次**（`chat-stream.js:65`），绝不实时朗读 |
| 用户误点后关不掉 | 页面一直出声，尴尬 | 播放中按钮明确变「停止」；切视图/清空对话自动停 |
| 切换视图后音频残留 | 多条音频叠加 | 全局单例播放器，任何导航动作先 `stop()` |
| 缓存目录膨胀 | 磁盘占用 | LRU 30 天过期 + 后台清空按钮 |

## 八、验收方法

1. **范围验收**：确认「听」按钮**只**出现在 AI 回答和营养师消息上，用户消息、系统消息上**没有**
2. **文本质量验收**：造一条含加粗 / 列表 / 表格 / 代码块的回答 → 播放，确认没有念出星号、竖线、反引号等符号；表格位置能听到「此处有一张表格，请查看屏幕」
3. **分段验收**：造一条 800 字长回答 → 确认分段处无断句、无重复、无明显停顿
4. **成本验收**：同一条回答连续听 3 次 → 后端日志确认**只调用了 1 次腾讯云接口**（缓存命中）
5. **降级验收**：清空 SecretKey → 确认按钮**直接消失**，而非点了报错
6. **真机验收**：微信内置浏览器（项目主战场）iOS + Android 各一台，验证自动续播是否被拦、锁屏后是否中断
7. **无回归验收**：`tts_enabled=0` 时前台与改造前**完全一致**（无多余 DOM、无多余请求）
