# 人工客服体系化升级计划（v2 规划）

> 基于：现有 handoff 模块源码事实（`services/handoff_service.py` / `routes/handoff.py` / `routes/admin_handoff.py` / `static/consultant/`）+ 业界成熟的人机协同客服体系（分层服务、坐席工作台、SLA 度量、AI 辅助闭环）。
> 目标：把"一点点搭出来的功能"升级成"有分层、有度量、有闭环"的客服体系，**不推翻现有架构**。

---

## 0. 业务假设（规划前提，与现状对齐）

- 用户端：微信 H5，健康/营养咨询场景，涉及隐私数据
- 坐席规模：1-3 名营养师（PC 工作台足够），短期不做呼叫中心
- 部署形态：单体 Flask + SQLite + gunicorn 2 worker，单实例
- AI 能力：Coze Bot（已有营养咨询专用智能体 `handoff_ai_agent_id`）

这四个假设决定了：**不引入 Redis/MQ/WebSocket 集群方案**，所有升级在"轮询 + DB 状态源 + 单实例"边界内完成；假设变化时按 §6 重新评估。

## 2. 设计原则（所有阶段的共同约束）

1. **DB 是唯一状态源**：继续沿用"轮询 + SQLite"，前端状态只是体验层；新增功能不得引入内存态真相。
2. **AI 辅助、人工确认**：AI 可以给坐席生成草稿、给用户触发建议，但转人工后**永远不由 AI 静默替真人回复**（现有设计 §16.1 已确立，保持）。
3. **隐私最小暴露**：坐席看得到的内容按需最小化；导出永远走审计。
4. **小步可验证**：每阶段独立可上线、可回滚，测试先行（延续 `scripts/test_handoff.py` 模式）。
5. **改前端 JS 必升 `?v=` 版本号**（项目缓存破坏铁律）。

## 3. 分阶段路线图

> 排序逻辑：先堵隐私漏洞（红线）→ 再补运营闭环（看得见）→ 再提坐席效率（用得顺）→ 最后深化 AI 协同（锦上添花）。

### 阶段 0 · 地基修复（1 个迭代，改动小、风险低、必须先做）

**目标**：堵住权限红线，让配置回归后台自助，测试信号干净。

| 改动 | 文件 | 说明 |
|---|---|---|
| 坐席白名单制 | `services/handoff_service.py` `set_agent_status` | 不再自动 INSERT：未在 `cs_agents` 表的管理员点上线 → 403"尚未开通客服权限"（回到设计文档 §14.3 本意） |
| 坐席管理界面 | `templates/admin.html` + `static/js/admin.js` + `routes/admin_handoff.py` 新增 CRUD | 最小可用：坐席名单列表、添加/移除坐席、设置 max_concurrent；复用 `admin_required` |
| 转人工设置界面 | `templates/admin.html` + `static/js/admin.js` | 把已有 `GET/PUT /api/admin/settings/handoff` 接口接上 UI：总开关、专用 AI 下拉（读 `/api/admin/agents`）、四个文案、live_wait_sec/avg_handle_sec |
| 测试去 flaky | `scripts/test_handoff.py:242` | 读接口前先显式触发一次写路径（或调用 `_reconcile_locked`），消除与后台线程的竞态 |

**验收**：非坐席 admin 无法上线；全部配置后台可改；`test_handoff.py` 连续 3 次全绿。
**不做**：不动状态机、不动前端会话逻辑。

### 阶段 1 · 运营度量闭环（看得见的下一步）

**目标**：回答三个运营问题——"用户等多久？""营养师服务得好不好？""什么时候该加人？"

| 改动 | 说明 |
|---|---|
| handoff 统计接口 | `routes/dashboard.py` 新增：今日咨询量、排队 P50/P95 等待、首次响应时长（enqueued→active 或首条 agent 消息）、处理时长、关闭原因分布、留言占比、坐席负载与接待量 |
| 后台统计卡片 | admin.html 仪表盘加"人工咨询"区块；数据全部由 SQL 聚合，无新表 |
| 人工会话满意度 | 会话 closed 后前台弹一次轻量评分（复用 `satisfaction_surveys` 表加 `source` 字段区分 AI/人工）；dashboard 分开展示 AI 与人工 CSAT |
| 服务时间 business_hours | 落地设计文档 §6.3：`/api/handoff/config` 返回服务时段；非服务时段前台直接引导留言/留资，不再进 live 等待；后台可配 |

**验收**：dashboard 能看到上述指标；人工会话有独立 CSAT；非服务时段发起转人工直接落留言并明确告知原因。

---

### 阶段 2 · 坐席效率工具（用得顺）

**目标**：把营养师从"纯手打"升级到"有武器"，单位时间接待量提升。

| 改动 | 说明 |
|---|---|
| 快捷话术库 | 新表 `handoff_quick_replies`（标题/内容/排序/启停，后台可管理）；工作台输入框上方常驻一排可点击话术；**AI 辅助初始化**：可选一键用 Coze 从历史人工回复中提炼候选话术，管理员审核入库 |
| 内部备注 | `handoff_messages` 新增 `sender_role='internal'`（仅坐席可见，不入用户侧与导出）；右栏加备注输入 |
| 会话转接 | `POST /api/admin/handoff/<id>/transfer`：active 会话在坐席间转移（释放原坐席负载、目标坐席收通知）；解决"答不了只能关" |
| 图片消息 | 人工通道支持图片：复用现有 `/api/admin/upload` 与 `image_service` 压缩链路；`handoff_messages` 加 `attachment_url`；前台聊天与工作台渲染缩略图、点击放大。**安全**：附件走上传 URL，不存 base64；用户侧上传走已有 guest 鉴权 + rate_limit |
| 留言多轮 | 去掉"一回复即关闭"：留言首次回复后会话保持 open（`message` 模式），24h 无新消息由 reconcile 自动归档；用户可继续追问 |
| priority 启用 | 后台可对会话设置插队优先级（配合 `priority DESC` 现有排序即生效）；典型场景：老客户/复购用户标记 |

**验收**：营养师平均首响与处理时长（阶段 1 指标）可观测改善；一条会话内可完成多轮留言问答。

---

### 阶段 3 · AI×人工深度协同（体系的价值放大器）

**目标**：AI 不只是"挡在人工前面"，而是贯穿 服务全程的协同层。

| 改动 | 说明 |
|---|---|
| AI 回复草稿 | 工作台右栏"AI 建议"按钮：把 AI 历史快照 + 用户最新消息发给 Coze 生成草稿，**填入输入框由坐席编辑确认后发送**（严格符合原则 2）；可一键开关 |
| 智能升级触发 | 三种情况自动建议用户转人工（仍由用户确认）：① 用户对 AI 回答点踩 ≥2 次同一会话；② AI 回答命中"无法回答/建议咨询"类话术；③ 差评原因包含"想要人工"。落点：前台在 AI 回答下方浮出"联系营养师"引导条 |
| 知识回流闭环 | 每周/按量把人工会话中高频问题（`handoff_messages` user 侧聚类 + Coze 归纳）生成"FAQ 候选清单"进后台审核流；审核通过进社区问答精选或热门问题——**人工坐席的答案变成 AI 的养料**，这是人机协同体系的核心飞轮 |
| 案例联动 | 人工回复若命中案例标签，自动在会话侧栏展示对应 `case_documents` 供坐席一键引用（复用现有 FTS 检索） |

**验收**：草稿采纳率可统计；转人工建议触发率与人工解决率形成对照报表；至少一批 FAQ 通过回流机制上线。

### 阶段 4 · 可达性扩展（按业务量启动，当前不急）

| 方向 | 触发条件 | 方案 |
|---|---|---|
| 坐席离线通知 | 业务量增至夜间也有咨询 | 接企业微信/钉钉群机器人 webhook（服务端在 reconcile 里检测新 queued 时推送，改动极小，无需 Web Push） |
| 移动工作台 | 营养师需要外出接待 | `/consultant` 响应式适配优先于独立 App；核心是消息列表 + 通知，PC 三栏降级为单栏抽屉 |
| 多实例部署 | 坐席 >5 或并发会话 >50 | SQLite → PostgreSQL + 状态锁外移；此时才考虑 SSE 替代轮询 |

## 4. 与成熟体系的对照（自检表）

| 业界模式 | 本项目落点 |
|---|---|
| 分层服务（AI 自助 → 人工实时 → 异步留言） | ✅ 已有，阶段 1 补 business_hours 补完时段维度 |
| 坐席工作台（上下文栏 + 会话列表 + 工具） | 骨架已有；阶段 2 补话术/备注/转接/图片 |
| SLA 与度量（等待/首响/CSAT） | 阶段 1 全量落地 |
| AI assist（草稿而非替代） | 阶段 3 |

| 知识库飞轮（人工反哺 AI） | 阶段 3 |
| 全渠道触达 | 阶段 4 按需 |

## 5. 里程碑与验收总览

```
阶段0 地基修复   ── 隐私红线关闭 + 配置自助 + 测试干净      （必须，最先）
阶段1 度量闭环   ── 指标可见 + 人工CSAT + 服务时间          （让运营决策有据）
阶段2 坐席效率   ── 话术/备注/转接/图片/多轮留言           （让营养师省力）
阶段3 AI协同     ── 草稿 + 智能升级 + 知识回流             （让体系自我进化）
阶段4 可达性     ── 企业微信通知等，按量触发                （不预先建设）
```

每个阶段独立交付、独立验收；阶段 1-2 顺序可互换（度量先行更利于证明阶段 2 的收益，故推荐 1→2）。

## 6. 风险与边界

- **SQLite 写锁**：阶段 2 的图片消息与转接都走短事务，`BEGIN IMMEDIATE` 模式沿用，无新增风险；真正天花板在 §4 阶段 4 触发条件里明确。
- **AI 草稿成本**：Coze 调用按次计费，草稿做成"坐席主动点击才生成"，不做自动预取。
- **隐私红线**：任何阶段都不放宽"导出不含 AI 对话、审计必记录"的既有约束；新增内部备注默认不导出，导出需显式勾选并审计。
- **不做清单**（明确写下防止范围蔓延）：智能质检、情绪识别、多技能组路由、独立移动 App、WebSocket 推送——当前规模下都是负收益。
