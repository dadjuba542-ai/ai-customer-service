# 大字·清晰版（适老化显示）实施方案

> 状态：**计划阶段，未实施** ｜ 建立日期：2026-09-10
> 目标：给中老年用户提供一键放大显示，命名体面（对外叫「大字·清晰版」，入口不点破年龄）

---

## 一、现状勘察（2026-09-10 实测数据）

| 项目 | 现状 | 对适老化的影响 |
|---|---|---|
| 字号写法 | **全部硬编码 px，无 rem 根字号** | 无法靠 `html{font-size}` 一键缩放 |
| CSS 字号数量 | 约 230 处（含 admin.css 63） | 手工改不现实，必须脚本批量 |
| 字号分布 | 12px×46、13px×47、14px×48、15-18px×50… | **60% 集中在 12-14px**，对老花眼是硬伤 |
| 字号变量 | `base.css` 的 `:root` 只有颜色/圆角/阴影，**无字号变量** | 需新增 `--fs-scale` |
| 内联样式 | `index.html` 仅 2 处；`templates/admin.html` 38 处 | 前台基本干净，后台可暂缓 |
| JS 动态渲染 | 仅 `news-discover.js:402`（词云）硬编码字号 | 影响面小 |
| viewport | `maximum-scale=1.0, user-scalable=no` | **禁止双指缩放，属无障碍缺陷** |
| 对比度 | `--slate-400: #9CA3AF`，白底约 2.5:1 | 远低于 WCAG AA 4.5:1 |
| 偏好存储 | 已有 localStorage 先例（`chat_profile`/`token`/`user`） | 可复用，**访客未登录也能记住** |

**结论**：改造基础不错（内联样式少、颜色已是变量），主要工作量在 230 处 px 的批量变量化。

## 二、技术方案

### 2.1 核心机制：`--fs-scale` 变量 + calc 乘法

```css
/* base.css :root 新增 */
:root              { --fs-scale: 1;    }
html[data-ts="l"]  { --fs-scale: 1.3;  }   /* 大 */
html[data-ts="xl"] { --fs-scale: 1.55; }   /* 超大 */

/* 全站批量替换：font-size: 14px  →  */
font-size: calc(14px * var(--fs-scale, 1));
```

**为什么不用 rem**：
- 改 rem 需要重算 230 处数值（16px→1rem），且 `font-size: 14px` 散落在 Sass 变量、媒体查询、简写 `font:` 里，人工改必出错。
- `calc()` 方案是**纯机械正则替换**，且 `--fs-scale=1` 时计算结果与原值**像素级完全一致** —— 这是天然的回归基准：切换前截图 A，开启后 scale=1 截图 B，A/B 相同即证明替换无副作用。

**为什么不用 `zoom` / `transform: scale`**：`#app-container` 是 480px 定宽移动端容器，整体缩放会横向溢出、点击热区坐标错位、fixed 元素乱飞。

### 2.2 三档参数

| 档位 | `--fs-scale` | 正文 14px → | 小字 12px → | 标题 20px → |
|---|---|---|---|---|
| 标准 | 1.0 | 14px | 12px | 20px |
| 大 | 1.3 | 18.2px | 15.6px | 26px |
| 超大 | 1.55 | 21.7px | 18.6px | 31px |

对齐工信部《移动互联网应用适老化通用设计规范》：正文 ≥18px（"大"档即达标）。

### 2.3 三层改造结构

| 层 | 内容 | 风险 |
|---|---|---|
| **① 全局层** | 脚本批量：`font-size: Npx` → `calc(Npx * var(--fs-scale,1))`；写双值 fallback（`font-size:14px; font-size:calc(...)`）兼容极老内核 | 低（scale=1 等价） |
| **② 补充层** `static/css/text-size.css` | 仅对 `html[data-ts]` 生效的覆盖：行距、点击热区、对比度、导航高度、卡片内边距、字重 | 中（需逐组件调） |
| **③ 隔离层** | 特殊件单独处理：Quill 富文本 `ql-size-*`、词云、弹窗、输入框 | 低（局部） |

### 2.4 补充层要做的事（不止是放大字）

单纯放大字会导致**文字撑破容器**，所以这层才是体验关键：

1. **行距**：固定 px 的 `line-height` 改为无单位倍数（1.5 / 1.7），随字号自动放大
2. **点击热区**：`nav-item`、`icon-btn`、标签 chip → `min-height/min-width: 44px`（WCAG 2.5.5 / 工信部 60px 建议取 44 兜底，导航可放宽到 52px）
3. **对比度**：`--slate-400` #9CA3AF → #6B7280（4.8:1），`--slate-300` 仅用于边框不用于文字
4. **容器自适应**：导航 5 个 tab 在超大档可能挤爆 → 超大档隐藏"发现/社区"文字标签只留图标，或 tab 改两行
5. **输入框**：`font-size ≥16px`（否则 iOS Safari 聚焦会自动放大页面，体验割裂）
6. **AI 回答区**：`.rich-text` 内 `ql-size-small` 等 class 在清晰版下重定义

### 2.5 切换入口

- **位置**：首页右上角常驻 `Aa` 图标按钮（`aria-label="清晰版显示设置"`）
- **交互**：点击弹出底部半屏面板 → 标题「字体大小」+ 实时预览示例文字 → 三档单选（标准 / 大 / 超大）
- **文案**：面板副标题「切换到大字·清晰版，阅读更轻松」—— 全程不出现"老年/长辈/关怀"字样
- **持久化**：`localStorage['ui_text_size']`，取值 `'' | 'l' | 'xl'`

### 2.6 防闪烁（必须做）

在 `<head>` 内、所有 CSS 之前插入内联脚本，读 localStorage 并给 `<html>` 打 `data-ts` 属性。
否则会出现"标准字号先渲染 → JS 加载后跳成大字"的闪跳，中老年用户会以为页面坏了。

```html
<script>
  try { var t = localStorage.getItem('ui_text_size'); if (t) document.documentElement.dataset.ts = t; } catch (e) {}
</script>
```

### 2.7 viewport 修正

```html
<!-- 改前 -->
<meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no">
<!-- 改后 -->
<meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=5.0">
```
放开双指缩放是无障碍底线（WCAG 1.4.4）。配合输入框 ≥16px 可避免 iOS 聚焦自动放大。

### 2.8 防误触与可退出设计（必须做）

中老年用户误触后如果切不回来，比不改更糟。四道保险：

| # | 措施 | 说明 |
|---|---|---|
| 1 | **Aa 按钮不参与缩放、位置固定** | 用 `transform: scale()` 反向抵消或直接写死尺寸；否则超大档时按钮跟着变大、挤压右上角，反而更难找到 |
| 2 | **切换后弹 5 秒"后悔条"** | 仅「标准 → 大/超大」时弹出，文案「已放大 · 点这里恢复」，点击立刻回标准，5 秒自动消失。切回标准时不弹，避免来回打扰 |
| 3 | **面板内"标准"档置顶 + 醒目标注** | 三档顺序固定为「标准（默认）/ 大 / 超大」，当前档位打勾。面板底部再加一个文字链接「恢复默认设置」 |
| 4 | **长按 Aa 2 秒强制回标准** | 隐藏快捷键，供慌张用户一键逃生，不占用可见 UI |

**兜底逻辑**：档位只影响 CSS，防闪脚本失效时 `<html>` 无 `data-ts` → 回落标准档。即 **JS 挂了也不会被困在大字模式**。

**不做自动开启**：不根据 UA / 系统字号自动切大字。误判代价太高（年轻用户看到大字会直接退出）。

## 五、验收方法

1. **无副作用回归**：`--fs-scale=1` 时全站截图 vs 改造前截图，应像素级一致
2. **计算值抽查**：`getComputedStyle` 验证关键元素字号 = 原值 × scale
3. **窄屏压测**：375px 宽 + 超大档，检查横向溢出、导航挤压、弹窗截断
4. **真机验证**：微信内置浏览器（项目主战场）+ iOS Safari 输入框聚焦不跳变
5. **切换不丢位置**：切档后聊天记录滚动位置按比例保持，不跳回顶部

## 六、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 批量正则误伤（`font:` 简写、`var()`、`inherit`） | 样式崩坏 | 脚本白名单跳过；替换后 `git diff` 人工抽检 + 截图回归 |
| 极老 Android 不支持 `calc()` | 该部分字号失效 | 双写 fallback（`font-size:14px; font-size:calc(...)`），老内核降级到前者 |
| 放大后固定高度容器溢出 | 局部破版 | P2 逐屏排查，统一改 `min-height` |
| 导航 5 tab 在超大档挤爆 | 导航不可用 | 超大档隐藏文字标签 / 缩图标 |
| iOS 输入框聚焦放大页面 | 体验割裂 | 输入框字号 ≥16px（大档天然满足，标准档需单独设） |

## 七、待确认（开工前）

1. **跨设备记忆**：一期只做本机 localStorage（零后端改动）。若要换手机也记住，需登录态 + settings 表，另开一档。
2. **后台是否同步**：`templates/admin.html` 有 38 处内联字号 + admin.css 63 处，建议 P4 单独排期。
3. **是否加"进门引导"**：当前方案只有右上角常驻入口。若担心老人找不到，可在身份门（选团队+姓名）加一行轻提示，但会多一步操作、可能降低转化 —— 建议先只做常驻入口，上线后看点击率再定。
4. **默认档位**：建议仍是"标准"，避免年轻用户一进来觉得字太大。

## 八、页面朗读（TTS）方案

> 结论：**需要调 API，但不需要新账号、新密钥、新供应商** —— 项目已接入腾讯云 ASR，TTS 可直接复用同一套密钥与签名代码。

### 8.1 为什么不能用浏览器原生朗读

`window.speechSynthesis`（Web Speech API）零成本，但**在微信内置浏览器不可用**：Android 微信用的是 X5 内核，对 Web Speech API 支持有限或完全不实现；iOS 微信同样有大量失效反馈。
本项目主战场就是微信内置浏览器（分享传播全靠它），所以原生方案**不能作为主路径**，只能作为非微信环境的加分项。

### 8.2 复用现有腾讯云凭据

现有代码已具备完整条件（`services/speech_service.py`）：

| 已有资产 | 位置 |
|---|---|
| 腾讯云 SecretId / SecretKey | `tencent_secret_id`（明文 setting）+ `tencent_secret_key`（加密 setting） |
| TC3-HMAC-SHA256 通用签名 | `speech_service._tencent_api_request(action, payload, secret_id, secret_key)` |

只需把函数里的三个常量参数化即可调用 TTS，**改动约 10 行**：

| 项 | ASR（现有） | TTS（新增） |
|---|---|---|
| host | `asr.tencentcloudapi.com` | `tts.tencentcloudapi.com` |
| service | `asr` | `tts` |
| version | `2019-06-14` | `2019-08-23` |
| Action | `SentenceRecognition` | `TextToVoice` |

### 8.3 接口与参数

`TextToVoice` 关键参数：`Text`（≤300 字符/次，长文本需分段）、`VoiceType`、`ModelType`（1 基础 / 2 精品 / 3 大模型）、`Speed`、`Volume`、`Codec`（mp3）。
返回 `Audio` 为 base64 编码的 mp3。

### 8.4 成本（2026-09 官方计费）

| 音色档 | 免费额度 | 后付费 |
|---|---|---|
| 基础 / 精品 | **800 万字符** | 0.3 元/万字符 |
| 大模型 | 10 万字符 | 0.4–1 元/万字符 |
| 超自然大模型 | 2 万字符 | 4.8–6 元/万字符 |

免费资源包需在控制台领取，**自领取起 3 个月内有效，一个账号仅一次**。

**估算**：一条 AI 回答按 500 字计，用精品音色 = 0.015 元/次；800 万字符免费额度约够 **1.6 万次朗读**。中小流量下前期基本不花钱。

### 8.5 实施要点

1. **后端**：新建 `services/tts_service.py`，参数化 `_tencent_api_request` 后调 `TextToVoice`；路由 `POST /api/tts`。
2. **缓存（重要）**：按 `md5(text + voiceType)` 缓存音频，同一条 AI 回答被多人听只计费一次。否则热门回答会重复烧钱。
3. **限流**：按会话 / IP 限制调用频次，防止被刷（沿用 `crawl_guard` 思路）。
4. **长文本分段**：>300 字按句号切分，合成后前端顺序播放。
5. **开关**：新增 setting `tts_enabled`，未配置密钥或关闭时**隐藏"听"按钮**，不留点了没反应的死按钮。
6. **前端**：AI 回答气泡下方加「🔊 听」按钮；播放中变「停止」。仅对 AI 回答和资讯正文开放，不做全页朗读（噪音大、成本高）。
7. **降级**：合成失败 → toast 提示「朗读暂不可用」，不影响其他功能。

### 8.6 建议节奏

朗读与字号是**两个独立能力**，不必捆绑。建议先上 P0–P3（大字清晰版），看使用数据后单开 P4 做朗读 —— 朗读的价值对不识字/视力极差的用户反而更高，值得单独排期验证。
